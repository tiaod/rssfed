# 前端列表渲染（六种视图 + 虚拟化 + 无限滚动）

> 本文是 `packages/nuxt-client` 列表实现的细节与取舍；架构不变量见 [ARCHITECTURE.md](../ARCHITECTURE.md)。

时间线、分类页、单源页、Bot 产出页共用 `packages/nuxt-client/app/components/EntryList.vue`：
**除「表格」外的五种视图（社交动态 / 瀑布流 / 博客文章 / 列表 / 图片）共用同一套虚拟化外壳**
+ 页尾骨架触底加载，**第六种「表格」视图改用 `UTable` 自带的 virtualize**（见下面「表格视图」一节）。
数据侧由 `useSyncedEntryList`（列表只在 `load()` 里整体替换，`grow()` 只往末尾接更旧的条目）
与 `useInfiniteList`（单飞防重入）提供。

## 虚拟化（为什么必须做）

列表用 **Nuxt UI 的 `ScrollArea`**（`items` + `virtualize`，内部就是 `@tanstack/vue-virtual` 的
官方封装，见 `EntryList.vue`），只渲染视口附近的条目：`lanes` 按断点给列数，`estimateSize`
估算未测量过的条目，真实高度由 ScrollArea 内部 `measureElement` 在渲染后记住。

选它而不是自己接 virtualizer：虚拟化这层逻辑（测量、overscan、scrollMargin、lanes 分配）
交给官方组件维护，升级 Nuxt UI 自动跟进。**没有用 `ScrollArea` 的地方只剩一点**：它自带滚动
容器，所以外层要给它确定高度（页面里是 `flex-1 min-h-0` 的列表容器 + 组件内 `h-full`）。

瓶颈不在滚动本身（滚动由合成器线程负责，DOM 多少都一样是满帧），而在**追加一批时要把整棵
已有 DOM 重新布局**，成本随条数线性上涨。手机视口（393px → 1 列）+ CDP CPU 降速 6x 实测：

| 条数 | DOM 节点（前 → 后） | 加载时长任务（前 → 后） |
| --- | --- | --- |
| 600 | 6975 → **196** | 5 次 / 76ms → **0** |
| 1200 | 13937 → **196** | 12 次 / 133ms → 1 次 / 50ms |

桌面 8 列同样恒定（801 节点，0 掉帧）。

`content-visibility: auto` 那类"跳过视口外元素"的取巧方案试过、不够用，已放弃：600 条有效，
1200 条仍有 111ms，且滚动 P95 从 18ms 涨到 25ms（视口外元素滚进来要即时布局）。

## 前五种视图共用一套虚拟化外壳

`EntryList` 接一个 `view` prop（`social` / `masonry` / `blog` / `list` / `table` / `image`，见
`app/utils/listViews.ts`），其中前五种只切换 **item 渲染组件** 与 **布局参数**
（`lanes` / `gap` / `estimateSize`），虚拟化、页头跨列、页尾骨架触底、浮层锚点这些逻辑一份不动。
切换按钮（`ListViewSwitcher`）放在各页导航栏的同步按钮旁。

**没有直接用 `UBlogPosts` / `UPageList` 当容器**，因为颗粒度对不上：虚拟化要的是「index → 一个 DOM
块」的映射（ScrollArea 决定渲染哪些 index，再对每个 index 调一次 slot），而这两个组件是
「数组 → 一整块 DOM」（`v-for` 全量渲染）。把全量条目交给它们就等于放弃虚拟化；自己算窗口再喂
给它们，则要面对它们写死的 grid 列数（`sm:grid-cols-2 lg:grid-cols-3`）和自己按视口算的 lanes 对不上。
`UBlogPosts` 的可视规格本身 ≈ `UBlogPost × N` + 一个 grid class，所以**复刻版式即可，容器不要**。

### 各视图的估算口径

估算必须和实际渲染高度一致（`estimateSize` 参与泳道分配，估不准列尾就参差）：

| 视图 | 版式 | 手机列数 | 高度来源 |
| --- | --- | --- | --- |
| 社交动态 | 信息流：头像占左栏 + 署名行 + 标题摘要 + 图片区（1 张按比例 / 2~6 张 3 列相册）+ 操作栏，外侧列 576、正文列 536 | 1 | 文字档 170（实测）+ 8 + 图片区（单图 min(448, 536 ÷ 比例)；多图 行数 × (536 − 2×6) ÷ 3 + 行间距） |
| 瀑布流 | 封面按原比例，卡片高矮不一 | 2 | 有封面 320 / 无封面 180 |
| 博客文章 | 多列等高卡片：封面压成 `h-36` 横条 + 标题摘要各截断 2 行 + 卡片固定 `h-[22rem]`；单列（<768px）不强制等高、没有封面也不留占位带 | 1 | 多列写死 352；单列按有无封面 336 / 192 |
| 列表 | 紧凑单行：小缩略图 + 标题 + 两行摘要 | 1 | 写死 96（行高固定） |
| 图片 | 按封面真实比例的瀑布流（不裁切） | 2 | 泳道宽度 ÷ 该条封面宽高比 |
| 表格 | 一行一条：来源 + 标题（后接浅灰摘要）+ 日期，单行截断 | 不参与（表格自身三列） | 写死 53（`td` 主题 `p-4` + 一行 `text-sm` + `divide-y` 的 1px） |

图片视图的比例取自列表查询 `images` 投影里**压缩后的 width/height**，所以图片还没加载时首帧布局
和总高度就是对的（Nuxt UI 官方的 masonry 例子给的是常数估算，靠渲染后测量纠正）。没有封面或
缺尺寸元信息的条目按 4:3 占位、**不过滤掉**——每页条数稳定，触底加载的节奏才不会被打乱。

博客视图那条约 144px 的封面带（没有封面时也补一条）只为**多列行对齐**服务；单列没有行可对齐，
占位带折叠、卡片高度交回内容（估算也按有无封面分档），免得白白占掉小半屏。

**社交动态**与卡片视图的差别在正文与封面的主次：作者行（头像 + 署名 + 相对时间）在最上面，
主体是标题 + 摘要，封面缩成圆角图贴在文字下方并限高（`max-h-80`）——卡片视图反过来让封面通栏
占住顶部。

外侧内容列固定 `max-w-xl`(576px) 并居中，手机与桌面都是同一条窄列（宽屏下不会把一行字拉成上百字）。
列内是「头像 + 正文」两栏：头像占左侧 40px（头像 32 + 间距 8），**署名、正文、图片、操作栏整块
与头像右边对齐** —— 正文实际可用 536px，左边缘统一，扫读时视线不用在头像和文字之间来回跳
（`items-start`：头像顶端与署名首行齐平）。宽度是按**右侧以后还要加一栏**（AI 摘要 / 标签趋势 /
推荐订阅）选的：1440 下 左栏 240 + 内容 576 + 右栏 ~350 还放得下；那一栏本身还没做，这次只把内容
列收窄到位。**分隔线挂在内容列上**（不是整条泳道），线因此不与面板同宽、与头像那栏对齐；
条与条靠它划分，所以 `gap` 为 0。

图片区按张数换版式（一条最多 6 张，再多只看详情）：

- **1 张**：按原比例上屏，但比例夹进 `[0.7, 2.4]`、高度上限 448（`max-h-[28rem]`）。长图（竖屏
  截图那种）与超宽横幅按原比例会占满几屏或压成一条细线，所以超出的部分交给 `object-cover` 裁掉；
  高度吃满上限时宽度跟着缩（竖图因此比列窄，跟参考的社交媒体一致）。
- **2~6 张**：3 列相册网格，**最后一行不足 3 张时横向拉满**（1 张跨满 → 3:1，2 张各跨一半 → 3:2），
  于是每行高度一致（列宽的 1/3），行与行不参差；格子里的图一律 `object-cover` 裁成格子比例。
  口径见 `utils/entryDisplay.ts` 的 `feedImageCell`（版式与估算共用同一份）。

图片的本地 blob URL 由 `composables/useEntryImages.ts` **按条目懒取**：列表投影只让 `enrichEntries`
解好了封面那一张（列表缩略图只需要它），其余几张只对真正渲染出来的条目取附件、并带附件级缓存。
不在 `enrichEntries` 里一次解完，是因为那会让每个视图每一页的首帧都为几十条 × 最多 6 张附件
去读 IndexedDB，把「先出字、再出图」的顺序反过来。

每条下面是一行操作栏：标为已读 / 未读、收藏、新窗口打开原文。三个动作都沿用详情工具栏那一套
记号（`i-lucide-circle` / `i-lucide-circle-dot`、`i-lucide-star`、`i-lucide-external-link`），
写入侧的口径（写用户状态库 → 就地改列表里那个条目对象 → 失败提示与回滚）抽在
`composables/useEntryActions.ts`，详情工具栏（`useEntryDetail`）与信息流条目共用一份。
配色刻意保持中性 ghost：信息流里绝大多数条目都未读，若沿用工具栏「未读 = 主色软底」，
整列会挂满高亮按钮成为噪声（状态另有作者行的圆点与整条淡显；星标只在收藏时亮 warning 软底）。

**只有正文是打开详情的热区**（作者行、操作栏、分隔线都不是）：这类「一条里有多块可点内容」的
版式用整条 `@click` 会把点击目标变含糊，热区因此是真正的 `<button>`（按钮里也塞不下操作栏的
`<a>`，作者行才没做成指向源站的链接）。相对时间只给「多新」的观感，精确日期放在 `<time>` 的
`title` 里。

这一档的判据是**列数**而不是 CSS 断点：`EntryList` 把 `laneCount` 传给 item，占位带显隐与
卡片是否固定高度都由它派生。曾经用 `sm:`(640px) 写过，而博客的单列/多列边界是断点表里的
768px，640~767 这段就成了「已经是单列、占位带却还在」——一条边界写两处迟早会错开。

窄屏单独收档：手机上瀑布流两列（`masonry` 断点表 `0 → 2`），卡片只有 ~170px 宽，所以
封面高度区间、内边距、标题/摘要字号都按窄屏降一档（都用 `sm:` 还原，桌面不受影响），摘要限 4 行，
否则一行标题要折四五层。博客视图手机保持单列，两档版式一眼可分。

切视图会 `:key="view"` 重建 ScrollArea（布局算法换了，重建比留着上一版的测量值干净），代价是
回到顶部——正是切换视图时预期的位置。重建会让之前那个 ResizeObserver 盯上已卸载的节点，所以
量容器宽度、挂 observer 的那段逻辑做成可重入的（`syncViewportMeasurement`），切视图后重新挂。

## 表格视图：UTable 自带的 virtualize

表格是一行一条的邮件客户端式排布（来源 / 标题 + 浅灰摘要 / 日期），它**不复用上面那套泳道虚拟化**：
泳道虚拟化的抽象是「index → 一个格子」，跨列的东西要按列复制占位（见页头）；表格的抽象是
「行 → table」，列宽、sticky 列头、`truncate` 能用的宽度都归 table 布局管，塞进泳道等于自己把
table 布局复刻一遍。Nuxt UI 的 `UTable` 自带 `virtualize`（同样是 @tanstack/vue-virtual），
「只渲染视口附近的行」这条口径不变。换成它要接受三条约束：

- **它的根节点就是滚动容器**：页面给的 `flex-1 min-h-0` 必须落在根上，所以 `EntryList` 关掉属性
  自动继承、对两个分支手工 `$attrs` 透传（多根节点的模板不会自动继承，丢了就没有确定高度）。
- **行高只能是常数估算**：这版 `UTable` 不逐行测量，`tr` 直接被写成 `estimateSize` 那个高度 ——
  单元格就用主题默认（`td` 的 `p-4` + 一行 `text-sm` + `divide-y` 的 1px = 53），文字一律单行截断。
  宽度同理得给确定值（`table-fixed` + `w-full`）：只给 `min-w-full` 时表格按内容最小宽度撑开，
  `whitespace-nowrap` 的单元格会把它推到几千像素，靠右的日期列当场滚出可视区。列宽写在 `th` 上
  （固定布局首行即列宽），两侧列在窄屏收窄、`sm:` 还原：手机上三列都留着，标题也还有一栏可用宽。
- **行上挂不了自定义属性**：已读淡显只能走 `meta.class.tr`（允许是以行为参数的函数）。选中高亮
  不做 —— 表格不参与宽屏三栏，点击一律弹窗，没有「左边哪一行对应右边正文」要指。

页头（单源页的订阅源描述）走 `#body-top` 当作表体第一行，页尾骨架走 `#body-bottom`，两者都仍在
滚动内容里、仍是「骨架进视口 = 触底」。`UTable` 只给行 `role="button"` + `tabindex` 而不给
keydown，Enter 由 `EntryList` 在根上代理。

## 宽屏三栏：列表视图 + 常驻阅读栏

只有**列表**视图在 ≥lg（1024px）时把内容区拆成两栏 —— 加上左侧订阅源侧边栏就是三栏；其余视图
（社交动态 / 瀑布流 / 博客文章 / 图片 / 表格）宽窄屏一律点击弹窗。它们的版式意图就是「一屏扫过
很多条」或「一条一条往下读」，再切掉四成宽度等于把版式毁掉。断点取 lg：`UDashboardSidebar`
主题本身就是 `hidden lg:flex`，lg 以下连侧边栏都没有，三栏不成立。

阅读栏（`EntryReaderPane`）由 **layout 渲染在页面面板的同级**，而不是塞进面板 body：它是一整栏，
自己的顶栏与页面导航栏并排、各自占满自己的列；放进 body 的话页面导航栏会横跨整行盖在它上面。
它常驻（没选中时显示占位提示，选中后原地换正文），并且**可以用把手拖宽** —— 直接复用
`UDashboardSidebar`（`side="right"` + `resizable`），与左侧订阅源栏共用同一套拖动、双击复位、
cookie 持久化（键 `dashboard-sidebar-reader-pane`），边框把手也是同一个组件。

拖宽的是**栏**，不是正文：正文列的宽度上限沿用通用设置里的「条目详情宽度」（弹窗用它控制窗口宽度），
超出的宽度由 `mx-auto` 两边留白 —— 栏可以很宽，一行字不会跟着拉成上百字。设置选「全屏」即不限宽，
与弹窗选全屏同义。

宽度默认按视口给 38vw，下限 20rem；**上限随视口走**（`readerPaneMaxSizeRem` =
`min(80rem, 视口 - 侧边栏 15rem - 中间那栏下限 18rem)`：1440 下 57rem、1920 下 80rem）。
固定上限两头都不合适 —— 小窗口上会挤没中间栏，大窗口上又拖不动；同一个表达式也作为 root 的
`max-width`（`:style` 传进去，与组件自己的 `--width` 由 Vue 合并）：cookie 存的是绝对值，窗口
变小后靠 CSS 这层压回去，同时两处口径一致，不会出现「拖了却不变宽」。

分不分栏由**三个条件同时成立**决定（`useReaderPaneMode`）：宽屏 + 列表页路由 + 生效视图是「列表」。
视图由 `useListViewState` 发布（五个列表页都走它）；路由是布局的第二把锁 —— 页面卸载时不清共享
状态，因为页面切换在 Suspense 下的挂载 / 卸载顺序不保证，谁清谁写会互相打架。
单源页上「正在读哪一篇」也写在路由里（`/rss/feed/:id/entry/:entryId`，见 `useEntryRoute`）：
那条地址是该页自己的详情地址，仍算列表页 —— 点开一篇的瞬间不该把阅读栏换成弹窗。
反过来，**地址里没有条目就不该有详情**：换源 / 换页时由新挂载的列表页兜底关掉正在读的那篇
（离开的页面自己的监听不可靠，被卸载时会连同已排队的 pre 监听一起作废），否则上一源的文章会
以弹窗形式落到新页面上。

视图发布还要等偏好读完：订阅源 / 分组的默认视图是异步读出来的，把解析完成前的暂定值
（全局默认）发布出去，三栏会在切页瞬间塌成弹窗、读完再弹回来（`useReaderPaneView` 的 `ready`）。

**两个展示面互斥挂载**（`v-if`，不是隐藏）：打开即已读、全文懒取、弹窗那条浏览器返回键都挂在
展示面上，同时挂载会让同一篇被处理两次（历史栈会多压一条）。它们共用的口径 —— 打开即标已读、
按 id 懒取全文、上一篇/下一篇、已读与收藏切换 —— 收在 `useEntryDetail` 一份。带着正在读的那篇
切视图，正文会在阅读栏与弹窗之间交回（`closeEntry()` 只置 `isOpen`，所以阅读栏顶栏一律认
`isOpen && currentEntry`，否则空态会显示上一篇的源名、动作还会作用到那篇上）。

列数断点表不用改：阅读栏只出现在「列表」视图，而列表视图恒为单列（多列视图不参与分栏，
它们的列数口径仍是视口宽度）。

列表里正在读的那条加一圈高亮（`selectedId`）：三栏下正文在右边，没有这个标记就不知道对应左边哪一行。

## 视图默认值：三层 + 会话内覆盖

生效优先级（越具体越优先）：

    单源页 / Bot 产出页：订阅源 -> 所属分组 -> 全局 -> 瀑布流
    分组页：            分组 -> 全局 -> 瀑布流
    时间线：            全局 -> 社交动态

时间线那一层的落点与其它页不同：它是各源混在一起的信息流，内置默认取**社交动态**
（`TIMELINE_DEFAULT_VIEW`），其余页面兜底仍是瀑布流。要做到「没配过」不落到瀑布流，全局那一层
必须是**可选**的（`AppSettings.view?: ListView`，默认无值）：`undefined` 表示用户没配过，
显式配成瀑布流是另一回事 —— 通用设置页的下拉为此多一项「跟随内置默认」（哨兵值，见 profile.vue）。

存储位置分别是：全局在 `useSettings` 的 localStorage（`AppSettings.view`，通用设置页可改）；
订阅源在订阅文档上（编辑订阅弹窗里的「默认视图」，跟着用户状态库双向同步，不用改服务端 schema）；
分组新开一种用户状态库文档 `pref:group:<name>`（订阅管理页分组行的菜单）。分组是订阅文档上的
自由文本 `category`，所以分组改名后偏好会留在旧名字下成为孤儿，不做自动跟随。

**页面上的切换按钮只写会话内的 `useState` 覆盖**（`composables/useListView.ts`），刷新即回到配置值；
菜单里给「恢复默认视图」做会话内撤销。这样顺手点一下不会把配置改掉——默认值只能由三个显式入口修改。

## 已读 / 收藏

存储在用户状态库的 `entry-state:{entryId}` 文档里（双向同步），与条目本体库（单向同步）分库；
两者的写入不变量见 [ARCHITECTURE.md](../ARCHITECTURE.md) 的「用户状态库」。

列表查询在 `enrichEntries` 里按**当前窗口**的 id 批量合一次 `read` / `starred`：只查这几十条、
不扫全库；取不到就按未读处理，列表照常渲染 —— 已读态是锦上添花，不该因为用户状态库没就绪就让
列表空掉。列表里已读条目淡显（`opacity-60`）、未读带一个圆点，六种视图样式一致；
「标为已读 / 标为未读」按钮（阅读栏顶栏、弹窗工具栏）沿用列表页「只看未读」开关那对图标
（`i-lucide-circle` / `i-lucide-circle-dot`，未读再加主色软底）—— 全站的已读态记号只此一套。

**打开即已读**（`EntryDetailModal.vue`）：弹窗打开、以及「上一篇 / 下一篇」翻到某篇时自动标已读。
就地改列表里那个对象（`openEntry` 传入的就是列表元素，共用引用），列表立刻淡显，不重查；
写库失败则回退，不显示没落盘的状态。弹窗底部工具栏另给「标为未读 / 标为已读」与星标两个按钮；
星标状态以本地库的返回值为准。

**只看未读**（`useUnreadFilter`）：纯客户端过滤**已加载**的条目 —— 已读态在用户状态库、条目在
本体库，map view 没法 join，服务端过滤要先全量取状态再反查条目，正好是列表要避免的开销。
往下滚照常 `grow()`，骨架可见就继续加载；正在弹窗里读的那一条即使已被自动标为已读也留在列表里，
否则它会当场消失、弹窗的翻页基准就没了。筛选是会话级状态（`useState`），页面之间来回跳不丢，
刷新即清空。空态要和「真的没条目」分开说，否则用户会以为订阅丢了。

**收藏页**（`app/pages/saved.vue`）：`querySavedEntries` 先按 `savedAt` 倒序取状态窗口，再分块
回查条目，窗口只在「本地实际存在」的条目上计数（状态可能指向还没同步过来的条目）；在弹窗里
取消收藏后，关闭弹窗时重查一次，条目随即从收藏夹消失。

**全部标记为已读**（`useMarkAllRead`）只处理**当前列表已加载的**条目：不做「该源全部历史」——
那要先全量查询再批量写，一个老源上千条文档，写入和随后的同步都会明显卡一下，而用户此刻看得见的
就是这一屏。写完就地改本地条目、**不重查列表**（重查会整体替换并跳回顶部，而用户只是点了标已读）。
批量写走一次 `bulkDocs`：先按 id 取 `_rev`、已经是目标状态的跳过，避免逐条 get+put 的 N 次往返，
也不会把已读过的条目重复写一遍同步出去。

## 导航栏的动作区

四个列表页的导航栏右侧统一是〔切换视图〕〔只看未读〕〔✓ 全部标记为已读〕〔⋮ 页面动作〕（`ListActionsBar`）。

「只看未读」是个开关（`aria-pressed` + 开启时高亮），筛选逻辑不在这里：页面用 `useUnreadFilter`
过滤已加载的条目后把**可见列表**交给 `EntryList`，同时把可见条数交给确认浮层 —— 用户看到几条，
浮层就报几条，实际写入的也是那几条。

「标记为已读」留在外面而不是收进菜单：它是一次点击的常用动作，而且**兼任同步状态指示** ——
同步中转圈并禁用（写入还在落盘，这时候标记没有意义），同步失败变红并换成警告图标，错误详情同时
出现在按钮 title 与确认浮层里。

点击按钮先在它旁边弹一个确认浮层（`UPopover`）：「把当前列表的 N 条标记为已读？」+ 取消 / 确认，
确认之后才抛事件。批量标记没有「全部撤销」，值得多这一步；N 就是这次会被写的条数。正因为它俩要共用
同一份同步状态，按钮和 ⋮ 才放在同一个组件里：状态来自 `useManualSync`，每个实例各持一份，拆成两个
组件就会出现「菜单里点了同步、外面的指示按钮不动」。⋮ 因此保持朴素的三点，状态不在两处重复显示。

菜单内容按页面能力拼：同步（单源 / bot 页叫「刷新订阅」）、编辑订阅，最下面一组是取消订阅 / 订阅；
时间线与分组页只有同步。页面状态（分组规模「N 个订阅源」、加载中的占位）排在动作区最左、紧挨
切换视图按钮：先看到「这是什么页面 / 有多少内容」，再是动作，动作本身仍集中在最右。视图切换是
高频的版式切换，不塞进菜单（见 `ListViewSwitcher`）。菜单项的事件由页面接（`synced` /
`mark-all-read` / `edit` / `subscribe` / `unsubscribe`），组件本身不认识 pouch 的读写。

## 页头随列表一起滚

单源页的订阅源描述 + 「访问网站」（`FeedHeader.vue`）不固定在列表上方，而是通过 `EntryList` 的
`header` prop + `#header` 插槽作为**虚拟列表的第 0 项**参与滚动：跟条目同在一个 `ScrollArea` 里，
往下读时一起移出屏幕。

难点在多列：虚拟化按泳道摆放条目，**单个 item 无法跨列**。页头因此按当前列数渲染同样多份——
只有第一份可见并撑满整行（`inlineSize: calc(lanes * 100% + (lanes-1) * gap)`），其余 `invisible`
但同样占高；于是每一列都从页头下方开始，视觉上是一条贯穿整行的页头，而不是被挤进第一列的格子。
列表为空时页头仍固定在「暂无条目」上方（没有可滚动的内容）。

## 「已同步 N 条」提示条：浮层 + 滚动方向显隐

同步只报数、不动列表（见 `useSyncedEntryList`），所以提示条 `NewEntriesBanner` 要同时做到
「看得见」和「不打断阅读」。列表页用它的 `floating` 形态：绝对定位盖在滚动区顶部、**不占布局
高度**，展开 / 收起既不推动内容也不惊动虚拟化（实测展开前后卡片位置与 `scrollHeight` 都不变）。

**挂载那一次有个额外规则：先上屏、再优先同步**（`useListFirstPaint`）。单源 / 分组 / Bot 产出页进入时
先把该列表的源插到同步队列最前（`syncPriority`），但**等不等它取决于本地有没有缓存**：有缓存就一个
请求都不等、直接渲染，新条目照常折叠进提示条；本地空的（只有「暂无条目」可看）才等它跑完（最多 5s）
把内容直接上屏，不折叠。这样点进一个列表既不会先空白几秒，也不会把正在读的内容推走。

正因为不占布局，它才敢再叠一层滚动方向显隐（`useScrollHideOnDown`：下滑让位、上滑或回到顶部
露出）；页面在计数变化时调一次 `reveal()`，避免用户正好在下滑时漏掉这次通知。`reveal()` 之后
还有 1.2s 保护窗口——惯性滚动一秒能刷出几十个 scroll 事件，不留窗口的话新提示会被同一段下滑
手势立刻收走（实测表现是「闪一下就没，停手也不会回来」，用户只会觉得提示丢了）。

四个列表页（时间线、分类、单源、Bot 产出）都用这个浮层形态，页面侧统一走
`useEntriesBannerVisibility(count, anchorRef)`：它把方向显隐和「计数变化先露一次」组合在一起，
使用方只要给列表容器加 `relative`、给提示条传 `floating` + `:visible`。

组件仍保留常驻形态（`floating` 默认 false），但它**不按方向隐藏**：参与布局的元素改高度会让
滚动内容整体重排，虚拟化尤其怕这个（组件注释里记了试过的两版失败方案）。两种形态也都不能塞进
`EntryList` 的 `#header` 插槽——那样滚下去就看不见了，展开还会把正在读的内容推走。

浮层与列表分支的**渲染位置**也有讲究：它必须和列表容器一起提到空态 / 列表分支之外。列表为空时
同步带来第一批条目，`newCount` 已经变正却没有任何提示可点，页面会一直停在「暂无条目」
（`entries` 只在 `load()` 里更新，用户没有别的入口把它刷出来）。

## 页尾加载骨架 = 触底信号

`hasMore` 为 true 时，列表末尾排**每列一个**加载骨架（列数等于骨架数：虚拟化按「最矮泳道」分配，
N 个等高的骨架必然一列落一个，滚到底部时每列都有东西，也就不需要列尾补平）。它们当作普通条目
参与虚拟化，**任一骨架进入视口就等于「用户滚到底了」**，由 `EntryList` 里的
`useIntersectionObserver` 触发加载。

不用 `rootMargin` 提前 N 屏的原因：IntersectionObserver 的相交判定还要与 target 的所有滚动
祖先裁剪框求交，root 用隐式视口时内部滚动容器会把它挡住——实测「必须滚到底才触发」，把 root
换成滚动容器才有效，但真实布局里到底哪个元素在滚并不好判断。骨架可见这个信号本身就在容器
可视区内，绕开了这一整类问题。实现里只留 200px 的 `rootMargin` 当缓冲，不是提前几屏预加载。
