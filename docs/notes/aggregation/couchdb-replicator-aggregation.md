## 背景

需求是把「服务端逐条读写搬运条目」换成 CouchDB 复制：每个（用户 × 源）一条 continuous 复制任务，
附件走 CouchDB 内部多部分传输（二进制、不经我们进程），窗口过滤挂在源库设计文档的过滤器上。

要保住的语义（当前设计承诺的）：用户库 = 源库在「当前窗口」内的投影 —— 新条目到达、源端删除跟随、
缩窗剪枝、放大窗口回填历史、重建 / v1→v2 迁移能把内容重新拉一遍。

实现已经写完（`git stash list` 里的 `stash@{0}`，未提交），整套 e2e 44 项里 42 项通过。
剩下两项失败 + 一个反直觉现象，促使我写了下面三组探针，把 CouchDB 复制的边界量清楚。

## 环境与复现

* CouchDB 3.5.2（单节点 Docker，`admin:admin`，`http://localhost:5984`）
* 探针只用 raw HTTP，不依赖仓库任何代码；临时库跑完自动删掉

```bash
cd report/aggregation-replication
node probe-1-filter-and-deletions.mjs    # 过滤器与删除跟随
node probe-2-checkpoint.mjs              # 复制 id / checkpoint / 怎么强制重扫
node probe-3-restore-limits.mjs          # 目标端删过的文档还能不能回来
```

每份输出都存成了 `probe-N-output.txt`，本文引用的数字就是它。

## 结论 1：Mango `selector` 复制不搬删除（`probe-1` ①②）

| 复制方式 | 窗口外条目被挡住 | 源端删除传到目标端 |
| --- | --- | --- |
| `selector: {$or:[{type:'feed'},{type:'entry',publishedAt:{$gte}}]}` | ✓ | **✗ 传不过去** |
| `filter: 'main/timeline'` + `query_params.minPublishedAt` | ✓ | ✓（404ms） |

原因很直接：文档被删掉之后只剩 `_id/_rev/_deleted`，selector 没有任何字段可以匹配，
那条 `deleted:true` 的变更会被静默跳过。目标端于是永远留着源端已经删掉的条目。

→ **窗口过滤只能用源库设计文档里的 JS filter**，并且过滤器第一件事就是放行删除：

```js
if (doc._deleted) return true;
if (doc.type === 'feed') return true;
if (doc.type !== 'entry') return false;
return typeof doc.publishedAt === 'string' && doc.publishedAt >= req.query.minPublishedAt;
```

## 结论 2：`query_params` 里不能有叫 `since` 的参数（`probe-1` ③）

`probe-1` ③ 把窗口下界的参数名从 `minPublishedAt` 换成 `since`，结果**窗口彻底失效**：
窗口外 60 天的 `entry:old` 照样被搬进目标端（删除跟随仍然正常，406ms）。

因为复制协议会把自己的 `since`（`_changes` 的起始序号）传进 `req.query`，跟我们的参数同名互相覆盖，
过滤器拿到的是序号字符串，`publishedAt >= "0"` 恒真。

→ 参数名必须避开 `since`；实现里用的是 `minPublishedAt`。

## 结论 3：复制 id（参数哈希）与「怎么强制重扫」（`probe-2`）

`probe-2` 用「先把目标端文档 purge 掉（不留 tombstone，见结论 4），再看它会不会被重新搬回来」来判断
复制器有没有真的从 0 重扫：

| 步骤 | 复制 id（哈希） | 结果 |
| --- | --- | --- |
| ① 窗口 3 天，`generation=g1` | `9a44f845…+continuous` | 只搬窗口内的新条目 |
| ② 同参数，只换复制文档 id | 同一个哈希 | 不重发（共用 checkpoint） |
| ③ 只把 `generation` 换成 `g2` | `c5d07f20…+continuous` | **从 0 重扫 → 被 purge 的条目 405ms 回来** |
| ④ 完全相同的参数重建 | 同一个哈希 | 沿用旧 checkpoint，什么都不重发 |
| ⑤ 删掉两端 `_local/<哈希>` 再同参数重建 | 同一个哈希 | 从 0 重扫 → 1212ms 回来 |

两条要点：

* 复制 id 由 **源库 + 目标库 + 过滤器名(+continuous) + query_params** 决定，**与复制文档 id 无关**。
  所以「删掉任务再建一条一样的」不会重扫；把 `generation` 编进 `query_params` 才会换哈希。
* `checkpoint` 就是两端 `_local/<哈希>`，删复制文档不动它；显式删掉它也能强制重扫（⑤，备选手法）。

## 结论 4：目标端删过的文档，全量重扫也回不来（`probe-3`，最关键）

| 步骤 | 观察 |
| --- | --- |
| ① 首次复制 | 源端 rev `1-e836bbbe…` = 目标端 rev `1-e836bbbe…` → 复制固定以 `new_edits:false` 写入 |
| ② 目标端删 `entry:a`（tombstone）、purge `entry:b` | tombstone **不在 `_all_docs` 里**（扫描结果直接消失），只在 `_changes` 里：`{id:'entry:a', rev:'2-1556f05f…', deleted:true}` |
| ③ 换代次强制全量重扫 | 被 purge 的 `entry:b` **4.0s 回来**（证明这一轮确实全量重扫了）；被删除的 `entry:a` **不回来** |
| ④ 把 `entry:a` 的 tombstone 也 purge 掉，再重扫 | **4.4s 回来** |
| ⑤ 复制文档里加 `new_edits: true` | 被接受、但**被忽略**：目标端 rev 仍与源端一致 |
| ⑥ 目标端再删一次 `entry:a`，改源端产生新 rev | 目标端 4.0s 跟上新 rev —— 「复活」的唯一途径 |

原因：`new_edits:false` 意味着目标端认识那个 rev；它已经把这个 rev 删成了 tombstone，
重发同一个 rev 就是空操作。**源端不产生新 rev，这个文档在目标端就永久消失。**

→ **复制是「变更投递」，不是「投影」。** 想恢复一个目标端已经删掉的文档，唯一原语是先 `_purge`
掉目标端那份（抹掉 rev 记忆）再换哈希重扫；tombstone 要去 `_changes` 里找，`_all_docs` 看不到。

## 这对当前实现意味着什么

已验证能工作的部分（e2e 42/44）：新条目到达、附件二进制原样搬运（源库、甲用户库、乙用户库字节完全一致）、
源端删除跟随（JS filter，406ms）、退订清理、缩窗剪枝、`wait=1` 在请求内跑完、客户端写方向闸门仍然生效。

两个失败项：

1. **「迁移清空后条目被重新搬回来」** —— 就是结论 4：清空用的是删除（留 tombstone），没有 purge，
   换代次重扫也带不回来。要修就得把「清空」从删除改成 purge，而 tombstone 只能从 `_changes` 里找。
2. **「退订后 FeedDoc 副本也被清掉」** —— e2e 里那次是任务正在首次扫描中的竞态；
   单独在服务层探针里跑这条路径（删订阅 → reconcile）时，复制任务、条目、FeedDoc 副本都清干净了。

还有一条**客户端侧的同构问题**：服务端剪枝（删除）会正常复制到浏览器，PouchDB 也留下 tombstone。
之后服务端即使 purge + 重扫把条目恢复了，浏览器本地那份 tombstone 的 rev 更高，会把恢复出来的分支
判成冲突分支、继续认为「已删除」——用户看到的效果是「放大了窗口却什么都没多」。
要修就得让客户端在窗口变化时 purge 自己本地的 tombstone，并在 v1→v2 迁移后解冲突。

## 结论 5：如果放弃「放大窗口要回填历史」，机制可以少掉一大半（`probe-4`）

先说清楚：「恢复已删文档」**没有任何需求要求它**，是我为了实现下面三件事自己加的前提：

1. 窗口设置：当前已提交的实现里，放大窗口会把窗口外的历史回填回来；
2. `POST /api/timeline/rebuild` + 设置页「重建」：语义是「清掉服务端内容重新拉一遍」；
3. 我自己设计的 v1→v2 迁移：要把老库里「我们自己写的 rev」换成源端 rev。

`probe-4` 量了三件事：

| 步骤 | 结果 |
| --- | --- |
| A) 只把窗口下界 3 天 → 70 天（不加任何 `generation`） | **哈希变了**（`ed1ef8d4…` → `115d265e…`），5 天前的条目 2422ms 自动回填 |
| B) 先删掉目标端的 `entry:mid`（剪枝），再放大窗口 | **回不来** —— 剪枝不可逆 |
| C) 「重建」= 删掉用户库再建空库，原任务不动 | 1621ms 把窗口内内容**全量重搬回来**（目标端 checkpoint 随库消失，复制器从最缺的位置开始） |

于是：

* **`generation` 完全不需要**：换窗口本身就换哈希、自动全量重扫；
* **`purge` 也不需要**：「重建」用「删库重建 + 把 `subscription:` / `entry-state:` / `group-pref:` 搬进新库」即可，
  比 purge 干净（连客户端那边的旧 rev / tombstone 都一起消失）；
* **迁移**走同一条「删库重建」路径即可，不必单独设计；
* 代价只有一条：**剪枝（缩窗、退订）用的是删除，删掉的条目不可逆** —— 放大窗口只改变「以后」的行为，
  已经剪掉的历史找不回来（`probe-4` B）。

唯一还需要客户端配合的地方：如果希望「重建」在浏览器上也真的看得见内容恢复，客户端得在重建时重置本地库
（本地那份 tombstone 的 rev 更高，会把服务端恢复出来的分支判成冲突）。这只出现在「重建」这一个重动作里，
不像路线 B 那样日常窗口调整也要客户端配合。

## 三条可选路线

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **A. 回到服务端写库**（现在已提交、e2e 全绿的那版） | 服务端读源库、按窗口写目标库；附件已在抓取时生成为二进制、原样搬运 | 保留约 150 行搬运代码（无 per-user 参数）；但窗口放大 / 重建 / 迁移语义完整 |
| **B. 复制器 + 接受「窗口单向」**（结论 5） | 稳态用复制器（JS filter）；剪枝=删除、不可逆；重建=删库重建；迁移=删库重建；不需要 purge / `generation` | 放大窗口不回溯已剪掉的历史；重建要搬用户意图文档、客户端需重置本地库 |
| **B′. 复制器 + purge + 客户端配合** | 在 B 基础上，为「放大窗口即回填」再补 purge 与客户端 tombstone purge | 三处隐性耦合（purge 的 rev、浏览器端 tombstone、迁移后的冲突），长期维护成本最高 |
| **C. 复制器为主 + 恢复走服务端兜底** | 稳态复制器，只有「恢复已删文档」时才走服务端自己写的那条路径 | 两条路径并存 |

现在这条建议要分情况说了：

* 如果「窗口天数」可以被定义成**单向的保留策略**（放大不回溯已剪掉的历史，要找回历史就按一次「重建」），
  那 **B** 是可行且最省的：不需要 purge、不需要 `generation`、不需要迁移，日常路径只有
  「一条连续复制 + 剪枝删除」，比已提交的服务端投影版还简单。
* 如果「窗口天数」必须是**可来回调的窗口**（放大就要看到更多历史），复制语义顶不住，
  B′ 的三处耦合是为了绕开这一点付出的代价，此时 **A**（回到服务端写库）更划算。

## 最终选择与落地（B 路线，已实现并验证）

用户对上面这些路线的裁定是：**「服务端聚合的数据库本来就是从全量 feed 里修剪出来的，客户端同步就直接
同步这个聚合的数据库，不做二次修剪」** —— 即接受 B：聚合库是源库窗口子集的**镜像**，剪枝归服务端，
客户端只做镜像，不做任何窗口判断，也不需要"恢复已删文档"这套机制。

落地形态（与其对应的实测依据）：

| 机制 | 实现 | 依据 |
| --- | --- | --- |
| 搬运 | 每个 (用户 × 订阅源) 一条 continuous 复制，源库设计文档里的 **JS filter** + `query_params.minPublishedAt` | 结论 1（selector 不搬删除）、结论 2（`since` 撞名） |
| 换窗口 | 复制文档 id 带 `windowDays`，窗口变了就是另一条任务（另一份参数 = 另一个哈希）→ 复制器从 0 扫源库 | probe-4 A（2.4s 自动回填） |
| 剪枝 | 服务端按窗口删条目（客户端跟随删除） | 结论 1（复制器不会因过滤变严而删东西） |
| 重建 / v1→v2 升级 | **换一个空聚合库**：把用户写的文档（`subscription:` / `entry-state:` / `group-pref:` …）搬过去、旧库删掉，复制器重搬 | probe-4 C（1.6s 全量重投） |
| 客户端 | 重建是异步入队的，客户端等库名变过来后丢掉本地缓存重新全量拉一遍 | 浏览器 tombstone 的 rev 更高，不重置就看不见恢复的内容 |
| 不需要 | `generation`、`purge`、tombstone 扫描、per-user 参数 | probe-4 A/B/C |

### 实现期间又量出来的两件事（都不是复制语义的问题，但会伪装成"内容丢了"）

1. **`_local/state` 读不到时必须当成"当前版本"**。老实现（v1）是**显式**写 `version: 1` 的，但
   `nano` 在文档不存在时可能回一个 `{error: not_found}` 体而不是抛错；把"没有 version 字段"当成 v1，
   会让**每个新账号的第一次 reconcile 都白换一次库**，并且与并发的写入抢库名 → 表现为"刚导入的订阅
   不见了"。修法：只有明确读到 `version: 1` 才升级。
2. **建库 + 登记库名要是一次 CAS**。解析库名的路径（订阅、聚合、代理）会并发走到"这一列还没有值"，
   各自建库、各自写列值，后写的赢 —— 先写的那个库就成了**没人指得着的孤儿**（用户的订阅确实写进去了，
   但之后所有读取都去另一个库）。实测残留过 5 个这样的库。修法：`UPDATE … WHERE <列> IS NULL RETURNING`
   抢占，没抢到的一方删掉自己刚建的空库、改用赢家的库。

### 验证

* 单元用例：`packages/hono-server` 201 项、`packages/nuxt-client` 516 项全绿（含"换库重搬保留用户状态"、
  "并发建库只留一个赢家"、"重建后客户端丢本地缓存重拉"）。
* 真栈端到端：`packages/nuxt-client/scripts/verify-timeline-sync.mjs`（隔离实例 + 独立 PG 库 + 独立 Redis）
  **44 项全过、连跑两次稳定**：单库下发 → 复制器搬运（JS filter / 窗口 / 附件字节一致）→ 删除跟随 →
