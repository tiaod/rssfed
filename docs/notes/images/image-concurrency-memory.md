# 图片压缩为什么要有进程级并发闸门

> 留档：2026 年一次针对「抓取时图片压缩把机器压到 OOM」的实测。**现行行为以
> `packages/hono-server/src/images/concurrency.ts` 为准**，本文只是当时量到的数字。

## 问题

一次图片压缩要把源图完整解码进内存，代价与「同时压几张」成正比。而抓取侧原本**没有任何
进程级上限**：`FETCH_CONCURRENCY`（默认 4）× 每篇 `DOWNLOAD_CONCURRENCY`（3）= 最多 12 张同时压。
生产机只有 2G 内存，还要和 CouchDB / PostgreSQL / Redis / Nuxt SSR 共用。

## 实测（4 核，4032×3024 PNG → 缩到 1200px → AVIF q45，同一进程连续压 12 张，走真实 `compressToAvif` 路径）

| 同时压几张 | 峰值 RSS 相对基线 | 12 张总耗时 |
| --- | --- | --- |
| 1 张 | +106MB | 2.7s |
| 2 张 | +234MB | 1.3s |
| 12 张（改前的最坏情况） | +451MB | 0.7s |

在 2G 的机器上，几百 MB 的瞬时尖峰就是「OOM / 不 OOM」的差别。

## 取舍

- **只限「同时进行」的操作数，不改单张参数**（宽度 / 质量 / 每篇体积预算都不动）：
  代价是图片处理变慢一点，换来内存上界从「抓取并发 × 每篇张数」这种**会随配置膨胀的量**
  变成一个固定常量。
- 默认按核数给：2 核 = 1，4 核 = 2，8 核以上 4（压缩是 CPU 密集的，也不该把核占满）。
- 用 `p-limit` 而不是自己写：限流器的边界（异常仍要放行名额、FIFO、并发数变更）没必要自己维护。
- **语义是进程内的**，跨进程不适用；也不该换成 BullMQ 队列 —— 限制对象是 libvips 的 native
  内存，Redis 看不见，而且这些操作本来就在 `rss-fetch` 的 job 里跑，再排一层队列只多一次
  Redis 往返和一份源图序列化。
